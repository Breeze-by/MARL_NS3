# BASE-01 停止归因与后续闭环验证方案

本方案先于新增运动回合保存。原始任务摘录见 BASE01_REQUIREMENTS.md。保持原 world、三个出生坐标、模型碰撞、摩擦、扭矩和加速度参数；不通过改环境或阈值掩盖失败。

## 第一项 原执行算法的仪表化停止诊断

1. 从 gazebo_ros_pkgs 3.9.0 固定源码构建独立命名的插件，保留原更新算法，增加接收计数、接收时刻、被物理更新消费的目标速度、实测轮速、内部速度状态和关节电机目标的只观测输出。系统安装插件不覆盖。
2. 先固定源码/工具 Git commit 和二进制 SHA256。启动后从实际 gzserver 的 maps 核对加载文件，保存源、构建、配置、驱动遥测和真实模型状态的身份。
3. 仍在原 world 生成 tb1/tb2/tb3；先检查传感器、TF、地图、Nav2、初始接触/间距及静止。取消目标并暂停所有 Nav2，不启动 HeadquartersControl。
4. 仅作停止诊断：三台在原地接受 angular.z=0.6 rad/s、linear.x=0 的受控指令，最多 4 秒仿真时间/12 秒墙钟时间。机器人不通过模型位姿设置移动，这也不记作自主探索。
5. 停止发送非零目标，维持 20 Hz 零命令。区分“发送”“话题观察”“驱动 OnCmdVel 接收”“物理更新消费”“轮/关节响应”“模型真实速度”，不能用前者代替后者。
6. 原停止窗口为 12 秒墙钟；三台必须各自具有新鲜完整样本，真实线速度 <0.01 m/s 且 |角速度|<0.03 rad/s，连续至少 1.5 秒墙钟且该稳定期内仿真推进 >0.5 秒。缺失、断流、时钟冻结、非有限状态均不通过。

## 第二项 有证据的最小修补

若诊断复现“驱动已经消费零目标，内部指令却产生非零/反向输出”的状态缺陷，应用已有的状态同步最小补丁，保留原速率/物理参数。独立编译固定的新二进制，在相同停止诊断协议下验证一次；若不通过，保留并继续针对实际失败归因，不宣布仅凭数值反例成功。

若旧算法停止诊断未复现，不为得到失败而自动扫参数；依据遥测决定下一项最小诊断。任何无法从数据证明的因果关系继续标明未确定。

## 中止与退出

出现底盘接触、机器人间距 <0.70 m、异常高度、关键观测丢失或节点/TF严重错误，立即结束受控运动并进入停止流程。停止失败时可物理暂停以收尾，但该回合仍 FAIL。只结束本回合跟踪的进程，不影响其他工作区。

## 第三项 修补版三机器人自主闭环

停止诊断通过后，在固定最终源码/驱动下运行三机器人：先非自主检查和可信静止，再恢复 Nav2、启动原 Frontier 控制器，最多 180 秒仿真时间和 420 秒墙钟时间。检查实际 goal/UUID/接受/反馈/结果/再次分配、逐台运动、SLAM和共享图更新、坐标与局部图范围、持续观测及最后可信停止。

形式上的启动或地图数组变化不足以通过。依据 BASE01_REQUIREMENTS.md 的 BASELINE SMOKE PASS 必要条件独立核对；不宣称完整地图任务完成。失败保留、定位、修补；充分通过一次后不再追加回合。最终更新 PROJECT.md 和交接报告，提交独立验收。
