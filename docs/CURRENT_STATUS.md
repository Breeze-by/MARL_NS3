# 三机器人探索与无线通信项目现状及部署差距

截至2026年11月13日。面向项目方案与下一步研究评估。当前工程入口与历史归档已整理，运行结果没有新增。

## 最重要的三个回答

**第一，ns-3已经真正接入原来的Gazebo三机器人探索导航系统。** 在联网运行中，机器人地图、定位信息、导航目标和执行反馈的消息内容，确实经过ns-3的Wi-Fi网络模型，再交给另一端使用。已经完成多次“机器人感知建图—中央选择目标—机器人导航—返回新地图和结果”的完整循环。

**第二，计算分工基本合理，但当前通信负载还不是实机部署所需的最精简方案。** 原始雷达、本地建图、路径规划和避障留在机器人端；中央根据共享地图和三机状态分配探索目标。这一结构适合真实机器人。与此同时，当前还传输了完整坐标变换、局部导航地图、速度观测副本、较大的机间避让地图，以及部分评价和运行记录，需要进一步厘清哪些是产品必需、哪些是研究原型附带的负载。

**第三，不能说“除仿真代码延时外，已经与实际部署一样”。** 当前仍是同一台主机上的联合仿真，通过消息适配程序把选定业务送入模拟Wi-Fi；三台机器人的计算与通信尚未像三台独立实机那样分开。无线传播、时间、定位标定和安全监督也存在明确的仿真假设。这些差异会改变信息到达顺序、系统负载乃至探索路线，不能简单减去一个固定的软件延时就消除。

目前最准确的项目定位是：**已经能够重复运行的三机器人探索与无线通信联合研究平台，尚不是已经完成实机等价验证的部署成品。**

## 已经做成了什么

三台Gazebo机器人各自使用360度二维雷达和SLAM进行感知、定位与建图。中央融合它们已经观察到的地图，找出已知与未知区域交界处的可探索位置，再由固定的强化学习策略为三台机器人选择目标。机器人收到目标后，仍由本机Nav2负责规划路线、避障和运动控制。

中央策略已经有训练得到的固定研究版本v1.1.0。强化学习只决定“下一步去哪儿”，不直接决定轮子怎么转，也不通过网络连续下发速度。通信研究期间沿用同一策略，避免把策略变化和网络变化混在一起。

无线接入已经超出了“网络仿真器在旁边运行”的阶段。系统传的是实际产生的地图、状态和导航任务消息，接收端使用的是经过网络模型交付的内容；并非收到一个通知后，再从源端的理想共享内存中取回原消息。导航目标的接受、执行结果和取消也有对应交互，而不是把“发出目标”当成“机器人已经执行成功”。

近期还解决并验证了运行结束后的资源收尾问题，使完整实验能够正常停止、保存记录和退出。这一改进提高了重复实验的可靠性，没有改变探索策略或无线参数。

## PPO的真实作用和现有证据边界

对最近六次Gazebo运行的212次真实推理做精确离线回放，64次新目标分配中54次仍有2-5个合法选项，10次只有一个。与相同观察、候选和约束下的传统方法相比，有38个目标不同。选中目标确实进入Nav2请求，没有被后处理悄悄换成另一个规则目标。机器人2和3的实际偏好也不能由一张固定候选编号排序表解释。

这说明PPO真实参与选择，但**尚不能证明它稳定提高Gazebo探索效率**。可达性、冲突处理、保持已有任务和最大参与数量已有规则保障，不能全部算作学习收益。旧三地图Gazebo对照中，PPO在两张图达到95%更快、一张更慢；追加训练也没有证明优于继承的已训练权重。具体见[独立选择审计](../policy-audit-01/REPORT.md)及[网络结构图](figures/ppo-policy-v1.1.0/README.md)。

当前可读结果集中于[中文通信对比图表](communication-comparison-zh/通信方式对比图表汇总.md)及[PDF](communication-comparison-zh/通信方式对比图表汇总.pdf)。旧的过程日志和原始试验数据保留在[历史归档](../archive/README.md)，不再把早期“尚未实现RL/ns-3”的项目状态当作当前结论。

## 机器人与中央现在怎样交换信息

ns-3应理解为“虚拟无线环境”，消息适配程序则负责把机器人软件产生的信息送进去、再把收到的信息还原出来。二者职责不同。

```mermaid
flowchart LR
    R["三台机器人本地<br/>雷达 SLAM Nav2 避障与运动"]
    RG["机器人侧消息打包与还原"]
    W["ns-3模拟Wi-Fi<br/>三个无线终端 无线接入点 中央有线端"]
    CG["中央侧消息打包与还原"]
    C["中央计算<br/>地图融合 探索候选 固定RL 任务管理"]
    R <--> RG
    RG <--> W
    W <--> CG
    CG <--> C
```

图画的是业务职责。当前这些角色仍在一台仿真主机上运行，两侧的消息适配也由同一个程序管理，并不表示已经部署了四台独立计算机。仿真计时、真值评价和独立停止监督另有连接，见后文。

| 信息 | 现在放在哪里或怎样传输 | 实际用途与判断 |
|---|---|---|
| 原始雷达扫描、轮子和驱动内部数据 | 主要留在各机器人本地 | 供本地建图、避障和控制使用，这样分工合理，不需要中央逐帧接管雷达。 |
| 每台机器人的SLAM地图 | 经模拟Wi-Fi上传中央 | 是中央共享地图和探索候选的原料，需要共享。中央不能凭未收到的地图补出未知区域。 |
| 位姿、速度和坐标变换 | 经模拟Wi-Fi上传中央 | 中央据此判断机器人在哪里、当前状态是否可信，以及如何把目标变换到各机坐标中。 |
| 本地导航代价图 | 经模拟Wi-Fi上传中央 | 用于现有目标可达性和合法性检查。它不是神经网络直接读取的全部内容，但会影响可选目标，不能随意删掉。 |
| 导航目标的接受、进度、结果和取消交互 | 在中央与对应机器人之间双向过网 | 让中央知道任务是否真正开始、完成或需要重新分配。 |
| RL产生的新探索目标 | 在中央转换成位置与完整导航任务，再经模拟Wi-Fi下发 | 机器人收到的是高层目标，不是神经网络内部向量，也不是轮速或连续速度指令。 |
| 机间避让地图、协作状态和时效信息 | 中央计算后，经模拟Wi-Fi分别发给三台机器人 | 当前导航和保护机制使用这些信息，是现有系统的业务依赖。每机都要以自己的实际收件判断新鲜程度。 |
| 速度指令的观测副本 | 当前也经模拟Wi-Fi上传 | 实际速度控制仍在机器人本地；上传的这份副本不直接构成当前RL决策特征，却占用链路。 |
| 中央融合地图的回传副本 | 当前经模拟Wi-Fi发回机器人侧的评价与记录部分 | 中央本来已经持有这张地图；这份下行副本不是中央RL或本机Nav2的必需输入，但当前评价会用到它。 |
| 部分中央任务记录 | 当前经模拟Wi-Fi下发 | 兼有记录和运行结束管理用途，不能全部当作无关日志直接关闭。 |

**并不是所有上传消息都原样送进神经网络。** 中央先把地图、机器人状态和可探索位置整理成策略输入，策略选出目标，中央再做合法性检查并下发。候选生成、编码和目标转换都在中央完成，不需要为了“经过网络”把中央内部计算反复传送。

目前采用经中央协调的协作方式，没有独立的机器人之间直接交换地图或协商任务的无线协议。例如，机器人1的位置上传中央后，中央生成机器人2的避让信息再下发，这属于间接协作。机器人2用雷达看见机器人1，则属于本地感知，不是通信。

### 通信设计哪些地方还需要收敛

当前业务不只是几组坐标。三台机器人会周期性接收整张机间避让地图，一张约160KB，明显大于一个高层导航目标；上传侧还包含完整坐标变换和本地导航地图。它们使原型便于复用现有导航逻辑，但未必是未来实机最经济的交互方式。

评价用的融合地图回传也会占无线资源。是否让机器人端接收中央已有的完整地图，应由实际应用需求决定，而不能仅因为现有评价程序放在这一端就永远保留。任务记录还有停止管理用途，若以后调整，也要先安排好相应功能。

因此，对“信息传输是否合理”的判断是：**感知和控制留本地、共享认知和高层任务经过无线，这个方向合理；具体传哪些完整数据、传多少、把评价放在哪里，尚未完成面向部署的最终设计。** 后续压缩、筛选或改变发送方式，应保持探索策略所需信息和目标检查的含义不变，并在所有对照条件下采用同一规则。

## 哪些数据可以独立传送以及为什么

合理的隔离要求是：中央不能用理想通道补齐无线没有交付的机器人状态和地图；机器人也不能通过另一条理想通道收到正常探索目标。这不等于仿真器之间的所有管理信息都必须经过被研究的Wi-Fi。

| 独立信息或功能 | 当前作用 | 必须理解的边界 |
|---|---|---|
| 共同仿真时间及推进协调 | 让Gazebo、ROS和ns-3在同一个时间体系内前进 | 不携带未交付的地图或位姿，但会影响何时决策、何时判定信息过期。它是仿真共同条件，不能说完全不影响策略运行。 |
| Gazebo中的真实机器人位置 | 更新无线模型中终端的位置，供评价和独立安全监督使用 | 用于模拟传播、评价和独立实验安全监督，不能作为中央丢失定位时的替代输入。实机中距离自然影响无线传播，不需要给RL提供这种真值。 |
| 参考真值地图和真实轨迹 | 计算覆盖率、地图质量、路程及间距 | 只用于评价，不用于生成探索候选或选择目标。 |
| 机器人本地停止及独立实验停止 | 在通信或仿真异常时取消任务、停止运动或结束实验 | 只能用于保护与终止，不能绕过无线继续下发探索目标。仿真中的全局真值监督和暂停能力，也不能直接当作实机保护已经验证。 |

这些边界已体现在关键业务的来源、接收和消费者分工中。现有路径审查与隔离条件下的断链测试支持：切断模拟无线后，所审查的业务不能改用理想直连继续交付；最新六个运动回合没有为此再次主动切断全网。

同时，三台机器人目前仍共享一个机器人侧ROS通信环境，只是按机器人名称区分数据；中央另行分开。**这不是三个独立主机、独立网络接口的完整隔离。** 当前关键机器人—中央业务通过了规定路径，不代表整个ROS系统的每一个网络包、所有可能新增的机器人间订阅都已经纳入无线模型。以后拆成独立端点时，需要再次核对这一边界。

还有一个影响结果解释的地方：现有覆盖率时间按评价端实际收到融合地图的时间计算，而那份地图本身有一次无线下行。评价端晚看到更新，可能既包含实际探索变慢，也包含评价地图晚到。后续应分开观察机器人实际探索进度、中央已获得的地图和评价端已收到的地图，不能把三者混成同一个时刻。

## 最新运行结果说明了什么

最近采用同一走廊场景、相同机器人起点、固定探索策略和相同导航配置，做了三轮配对。每轮分别运行本地网关和较好Wi-Fi条件，每回合180秒仿真时间。

“本地网关”仍保留消息打包、还原和任务管理，只不经过模拟无线。它不是消息零延迟、绝对成功的理想系统；也不是绕开全部适配程序的直接ROS通信。

| 配对 | 本地网关达到95% | Wi-Fi达到95% | 本地网关达到98% | Wi-Fi达到98% |
|---|---:|---:|---:|---:|
| 第一次 | 39.46秒 | 35.61秒 | 52.07秒 | 90.97秒 |
| 第二次 | 62.25秒 | 40.42秒 | 112.26秒 | 99.31秒 |
| 第三次 | 72.01秒 | 48.68秒 | 74.51秒 | 57.31秒 |
| 平均 | 57.91秒 | 41.57秒 | 79.61秒 | 82.53秒 |

六次都跑满了180秒并正常停稳退出，最终正确自由空间覆盖率为99.826%—99.955%。三台机器人都实际参与运动。共64个导航目标，62个成功、2个由导航系统中止，没有任务超时或遗留未结束目标。两个中止分别出现在本地组和Wi-Fi组。

另有一次实验准备错误发生在机器人尚未启动时，单独保留，没有计入这六个探索回合。更早出现的启动异常和等待过长也并非都已查明原因，因此这里的重复运行结论限于本次场景和运行窗口。

这些结果证明了当前场景下系统能够重复完成联网探索循环。**它们没有证明Wi-Fi提高了探索能力，也没有证明任意地图都能以相同效率完成。** 本地组自身的95%时间相差32.55秒；其中最慢的一次全部目标成功，说明不能只用导航失败次数解释耗时。首次可选目标和任务分工已经不同，随后路线和地图更新也随之分叉。

三对中Wi-Fi达到95%都较早，但达到98%的平均时间反而略晚。仅盯住一个覆盖阈值，会漏掉后续区域的长尾。六次均按时间预算结束，并未据此证明系统能在任意剩余未知区域条件下自行判断“完整探索结束”。

## 与实际部署还差在哪里

| 方面 | 当前仿真做法 | 为什么不能直接当作实机等价 |
|---|---|---|
| 机器人计算与端点 | 三机与中央的角色运行在同一仿真主机上，三机共享机器人侧通信环境 | 实机各自有独立处理器、操作系统、无线网卡和消息队列；目前的共同计算竞争和理想本地连通方式不同。 |
| 传输协议 | 当前把选定ROS业务消息交给适配程序，经ns-3中的TCP和Wi-Fi模型传送 | 没有把全部原生ROS网络流量、发现通信和真实网卡驱动完整搬入模型。若实机沿用适配方案，可复用业务语义；若改用ROS原生无线通信，要重新核对负载与交付行为。 |
| 无线环境 | 使用接入点和三个无线终端，按距离等参数模拟信号衰减，当前使用固定无线速率配置 | Gazebo里的墙不会自动成为无线模型中的墙体衰减。真实室内遮挡、多径、干扰、天线和网卡自动选速尚未按实际设备校准。 |
| 时间与运行速度 | 已建立共同仿真计时并受控推进；180秒仿真在本地组约需360秒真实时间，在Wi-Fi组约需408—420秒 | 实机不会停下来等仿真器算完，各电脑也有时钟偏差。当前健康时效主要按共同仿真时间判定，另用真实时间保护防止仿真卡住；这不等于真实机器人已满足同样的毫秒响应要求。 |
| 共同定位 | 使用固定初始位置和共同坐标标定来融合地图、转换目标 | 实际机器人需要可靠建立共同坐标，面对定位漂移、扫描噪声和重新定位；不能把已知仿真出生坐标当成已解决任意实机标定。 |
| 安全与评价 | 本地保护之外，仿真还有全局真值监督、物理暂停和完整轨迹 | 实机需要依靠本机传感器、停止机构和看门狗应对断网，不能依赖仿真器随时暂停整个世界。 |

因此，“扣除代码耗时后就与实机一样”不成立。联合仿真消耗更多真实时间时，程序处理信息的机会、某些按真实时间工作的定时任务及信息交付顺序也会变化。这种影响会进入后续观察和目标选择，不是一笔固定的延时可以事后减掉。

当前已经具备面向部署的几个重要基础：本地感知与控制、高层目标接口、带时间信息的状态共享、任务结果管理，以及独立停止能力的原型。但还需要完成端点拆分、硬件与传感器适配、坐标和时间校准、真实无线参数验证，以及实机本地保护测试。实机工作是后续部署阶段的任务，不是开展下一步仿真通信研究的先决条件。

## 原定研究内容还有哪些没有达到

| 原定内容 | 目前进展 | 尚未达到的部分及原因 |
|---|---|---|
| 三机器人自主探索导航 | 已有固定策略，最新六次运行完成了实际感知、目标分配和导航循环 | 最新通信重复只覆盖固定场景和预定随机条件，不能推到任意复杂环境或实机。 |
| ns-3接入并实际承载业务 | 已做到机器人—中央关键消息真实通过模拟Wi-Fi，三次联网运行都完整结束 | 尚未等价复现三台独立机器人的全部网络与计算行为。 |
| 找到无线约束造成的探索损失 | 已能记录通信、观察、目标和运动的变化，较差链路条件此前也做过有限尝试 | 最新共同配置的重复只比较了本地与较好Wi-Fi；无线成本、适配与计算同步影响、导航波动尚未完全分开，不能直接把耗时差称为无线损失。 |
| 在固定RL下优化通信 | 探索策略保持固定，已具备研究接口 | 尚未实施正式通信优化。需要先选定真正影响业务交付的瓶颈，不能通过改探索策略或挑实验成绩制造优势。 |
| 整图探索的可靠完成判断 | 最新回合都达到95%以上，最终覆盖接近完整 | 这些回合仍是按180秒预算结束，覆盖阈值不等于自然完成全部可达区域。 |
| 真实机器人与真实Wi-Fi部署 | 本地导航和高层任务分工具有可迁移基础 | 尚未进行真实硬件部署与网络校准，不能预测特定场地上的绝对覆盖时间、无线损失或安全表现。 |

当前主要问题已不是“机器人和网络是否接通”，而是：**当前业务负载是否代表准备部署的应用，以及信息经过各环节后，究竟怎样改变了中央所见的状态和后续路线。**

## 下一步评估应优先决定什么

首先确定准备部署的通信分工：继续使用明确的业务消息适配层，还是最终让原生ROS网络流量直接跨无线。两条路线的实际负载和隔离要求不同。随后把探索必需、安全必需、评价记录三类流量分清，确认评价安排不会被误当成产品本身必需的无线负担。

在这个边界固定后，用同一份业务输入比较本地传输、较好Wi-Fi和受限Wi-Fi，分别衡量消息等待、有效交付和信息新鲜程度；再把这些变化对应到中央观察、目标分配和机器人执行。这样才能判断该优先研究地图增量、状态交付、可靠性还是其他通信机制，而不是先选一个优化算法，再寻找有利成绩。

真实部署准备可随后分步推进：独立机器人端点、共同定位与时间、真实网卡和信道参数、机器人本地断网保护。它们不要求现在重训练RL，也不应在后续通信研究中悄悄改变固定目标分配规则。

**项目已经有了可工作的联合系统；下一步需要把“已接通的原型”进一步变成“业务边界清楚、通信影响可解释、部署差距可逐项消除的平台”。**
